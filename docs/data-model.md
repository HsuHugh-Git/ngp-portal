# 申請中心資料模型（草案）

適用範圍：NGP Portal「申請中心」模組，試點為**資訊需求申請單**（Odoo it-ticket 已不再使用，無取代或搬遷問題）。詞彙定義見 [CONTEXT.md](../CONTEXT.md)，架構決策見 [adr/](adr/)。

## 1. 資料表

### 需求類別（request_category）
| 欄位 | 說明 |
| --- | --- |
| id | 主鍵 |
| name | 類別名稱（如：故障報修、帳號權限、設備採購、新系統功能） |
| requires_approval | 是否需要簽核 |
| active | 是否啟用 |

由 IT 在申請中心後台維護，不寫死在程式。

### 申請（request）
| 欄位 | 說明 |
| --- | --- |
| id、number | 主鍵與對員工顯示的編號 |
| applicant_id | 申請人（Entra ID 物件識別碼） |
| category_id | 目前類別（IT 可重新分類） |
| stage | 進度（見第 2 節） |
| outcome | 結案結果，未結案為空 |
| current_approver_id | 目前核准人，不需簽核時為空 |
| created_at、closed_at | 時間 |

### 申請版本（request_revision）
| 欄位 | 說明 |
| --- | --- |
| request_id、revision_no | 同一筆申請的第幾版 |
| payload | 該次送出的表單內容 |
| opnform_submission_id | OpnForm 送出識別碼，**唯一**，用於重複送達去重 |
| submitted_at | 送出時間 |

附件不存連結，只記 OpnForm 檔名，使用者點開時由申請中心取檔轉送（見 ADR 0002）。

### 簽核（approval）
| 欄位 | 說明 |
| --- | --- |
| revision_id | 針對哪一個版本簽核 |
| approver_id | 核准人（建立當下的快照） |
| result | 核准／退回補件／否決，未決定為空 |
| comment、decided_at | 意見與時間 |

### 進度紀錄（stage_log）
只新增、不修改。欄位：request_id、from_stage、to_stage、actor_id、note、at。用於時間軸與稽核。

### 申請代碼（request_token）
| 欄位 | 說明 |
| --- | --- |
| token | 一次性代碼，放進 OpnForm 網址的隱藏欄位 |
| applicant_id | 產生代碼時登入的申請人 |
| request_id | 補件重送時指向既有申請，新申請為空 |
| expires_at、used_at | 到期與使用時間 |

Webhook 回來時以代碼還原申請人，**不信任表單內填的姓名**。代碼無效、過期或已使用則拒收。

## 2. 進度與流轉

進度：`待簽核`、`待指定核准人`、`待處理`、`處理中`、`等待申請人`、`已結案`。
結案結果：`已完成`、`無法處理`、`已取消`、`已否決`。

| 事件 | 從 | 到 |
| --- | --- | --- |
| 送出，類別不需簽核 | （新） | 待處理 |
| 送出，類別需簽核，找得到核准人 | （新） | 待簽核 |
| 送出，類別需簽核，找不到核准人 | （新） | 待指定核准人 |
| IT 指定後備核准人 | 待指定核准人 | 待簽核 |
| 核准人核准 | 待簽核 | 待處理 |
| 核准人退回補件 | 待簽核 | 等待申請人 |
| 申請人修改重送（新增版本） | 等待申請人 | 待簽核 |
| 核准人否決 | 待簽核 | 已結案（已否決） |
| IT 開始處理 | 待處理 | 處理中 |
| IT 需向申請人補問 | 處理中 | 等待申請人 |
| 申請人回覆 | 等待申請人 | 處理中 |
| IT 結案 | 處理中 | 已結案（已完成／無法處理） |
| 申請人取消 | 任何未結案進度 | 已結案（已取消） |
| IT 重新分類為需簽核類別 | 待處理／處理中 | 待簽核（或待指定核准人） |

「等待申請人」同時用於簽核退回與 IT 補問；以進度紀錄的前一階段區分來源。

## 3. 規則

- **核准人**：取申請人在 **Femas HR** 的直屬主管（經資料倉儲 `mart_hr.base_femas`）。AD 的主管只在到職當天寫入、之後不同步，故不採用為準。Femas 查無主管、申請人即最高主管，或與 AD 主管不一致時，申請照常送出，進入「待指定核准人」並提醒 IT 確認，不自動猜測。IT 可隨時改派核准人，核准人欄位為快照。
- **繞過簽核**：類別由申請人選，IT 在待處理階段可重新分類；改成需簽核的類別時，重新進入簽核。
- **重複送達**：以 `opnform_submission_id` 當唯一鍵，Webhook 重送視為同一筆，不重複建立申請或簽核。
- **直接送出**：未帶有效申請代碼的 OpnForm 送出紀錄一律拒收。
- **簽核方式**：單層、單一核准人。不含代理人（列為後續擴充）；催簽規則見 [notifications.md](notifications.md)。

## 4. 待確認

- IT 目前實際受理的需求類型清單，以及哪些類別需簽核（it-ticket 已不用，需向 IT 確認）。
- OpnForm Webhook 逾時（5 秒）後是否重試，與重試間隔，需實測。
- 隱藏欄位預填與一次性代碼流程，需原型實測。
- Odoo it-ticket 歷史資料：**決定不匯入**申請中心，資料模型不需要「匯入」欄位。Odoo it-ticket 已不再使用，不需保留舊資料，也沒有切換日進行中單據的問題。
- 免費版 2 帳號：表單維護者與服務帳號各一，IT 需接受共用維護者帳號。
